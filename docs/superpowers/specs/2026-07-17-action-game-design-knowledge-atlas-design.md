# 动作游戏设计知识图谱：产品与内容设计规格

- 日期：2026-07-17
- 状态：待用户书面复核
- 交付形态：可离线运行、可部署到内网静态服务器的网站目录
- 核心定位：持续新增和完善的动作游戏设计知识体系，不是课程

## 1. 背景与目标

现有资料由 6 篇 Markdown 和 31 个图片/GIF 组成，主题覆盖动作游戏分类、复合决策、战斗思路、低韧性 Boss、动作表现，以及稻叶敦志的制作理念。这些材料内容丰富，但来源、写法、颗粒度和概念口径不统一，不适合直接作为可持续维护的知识体系。

本项目要把现有材料整理为一个可交互探索、可横向比较、可搜索、可追溯、可持续扩展的动作游戏设计知识图谱。新同事快速建立整体认知是重要用途之一，但网站不采用课程结构，也不以一次性培训为唯一目的。

成功标准如下：

1. 现有资料达到“观点级完整”：可删除重复、铺垫和与知识无关的个人化叙述，但保留论点、限定条件、反例、分歧、引用和游戏案例。
2. 同一维度存在冲突或条件差异的观点被明确标注，并能回溯到来源。
3. 所有游戏示例进入案例索引并与相关概念建立关系。
4. 用户能从全局星图进入局部主题，也能通过游戏矩阵进行横向比较。
5. 后续维护者通过结构化 Markdown 新增或修改内容，一键生成新的静态网站，不需要手改 HTML。
6. 生成结果既能直接离线打开，也能复制到普通内网静态服务器分享。

## 2. 受众与阅读假设

默认读者玩过较多动作游戏，但没有系统的动作游戏设计知识。网站不能假设读者理解立回、霸体、硬直、削韧、定番、取消等专业词汇；术语应提供随点随看的解释，但不把正文写成零基础教程。

资深策划应能利用图谱关系、筛选器、案例索引、冲突卡和比较矩阵进行快速查阅。新读者与资深读者共用同一知识体系，仅通过信息层级和入口不同获得不同阅读深度。

## 3. 范围与非目标

### 3.1 本期范围

- 整理现有 6 篇资料及 31 个媒体文件。
- 建立结构化 Markdown 内容模型。
- 建立概念星图、节点详情、游戏比较矩阵、案例索引、冲突索引、术语解释、来源追溯、搜索和筛选。
- 提供一次点击的本地静态生成流程。
- 提供桌面端和小屏端可用的阅读界面。

### 3.2 非目标

- 不提供网页编辑后台、用户账户、数据库或多人实时协作。
- 不尝试从任意非结构化文章中自动推断可靠的概念关系。原始资料可以直接归档，但要进入正式图谱，维护者仍需按模板整理元数据和知识节点。
- 不把网站做成固定顺序的培训课程。
- 不对设计理论给出绝对正确性排名。
- 不依赖外部 CDN、在线字体、远程搜索服务或运行时网络请求。

## 4. 信息架构

### 4.1 一级知识域

首页以“动作游戏设计”为中心，第一环固定为六个长期稳定的知识域：

1. **类型与边界**：广义 ACT、大众认知 ACT、狭义/传统 ACT、AAVG、魂式框架、共斗、无双、动作射击、动作向 JRPG 等。
2. **复合决策与系统深度**：宽度、深度、反馈时间、反应频率、操控精度、外部规则、难度、反馈循环、清版与非清版、动作与外部系统互通。
3. **战斗思路**：立回、主动/被动断招、压制、浮空、压起身、秒杀、定番、固定流程及它们的组合关系。
4. **敌人与 Boss 设计**：敌群出手机制、韧性、回合制人形、拟似对等人形、读指令、脱离与反击、资源条压制和相关 Boss 案例。
5. **动作表现与可读性**：直观经验、FOV、相机、剪影、动势、特征帧、辅助 UI/音效、时间伸缩、震屏、特写、观赏性与可读性的平衡。
6. **制作方法与设计哲学**：制作人与导演分工、概念转向、愿景与用户需求、人才观、强化优点、实践学习、动作游戏 know-how、文化保存及业务方向。

一级知识域是导航骨架，不限制跨域关系。一个节点可以与多个知识域、案例和冲突相连。

### 4.2 信息深度

“由简到繁”通过节点内容层级实现，而不是课程顺序：

1. **一眼看懂**：一句定义、所属领域、关键关系、代表案例。
2. **展开理解**：详细解释、机制拆分、适用条件、常见误区、关联节点。
3. **深入研究**：冲突观点、案例全文、媒体、编者归纳和来源依据。

每一层都可以独立阅读。用户不需要按固定章节顺序前进。

## 5. 内容模型

### 5.1 文件类型

内容层采用结构化 Markdown，至少包含以下类型：

- `concepts`：概念、框架和设计原则。
- `games`：游戏或系列实体，用于统一名称、版本与矩阵维度。
- `cases`：具体游戏、角色、Boss、关卡或机制案例。
- `conflicts`：同维度观点冲突或条件差异。
- `sources`：原始文章、采访、演讲、视频及外部链接。

原始 6 篇资料继续保存在来源档案中，不直接充当正式知识节点。正式图谱只读取通过模板整理的内容文件。

### 5.2 通用字段

每个内容文件使用稳定且唯一的 `id`。通用元数据包括：

- 标题、别名和一句摘要。
- 所属知识域和信息深度。
- 标签、更新时间和复核状态。
- 父子、相关、支持、对照、适用、示例等关系。
- 引用的案例、冲突、来源和媒体。

概念节点正文使用统一结构：核心定义、详细解释、设计变量、适用条件、相关概念、案例、冲突、编者归纳、来源。

### 5.3 关系类型

首期关系保持有限、清晰，不开放任意关系命名：

- `parent_of` / `child_of`：层级关系。
- `related_to`：非层级的概念关联。
- `supports`：观点、案例或来源为另一节点提供依据。
- `contrasts_with`：可比较但不必然冲突。
- `conflicts_with`：同条件或相近条件下存在直接分歧。
- `applies_to`：机制或观点适用于特定游戏、场景或条件。
- `exemplified_by`：概念由案例具体呈现。

构建程序检查关系目标是否存在，并生成反向关系，避免维护者重复填写双向链接。

## 6. 来源、编者归纳与观点边界

网站严格区分以下内容：

1. **来源观点**：来自原文章、采访或视频的观点，显示作者和出处。
2. **编者解释**：为了帮助理解而重写的定义、转述或结构化说明。
3. **编者归纳**：跨资料总结出的关系、适用条件或综合判断，必须明确标注。
4. **案例事实**：游戏中的机制、行为和结果描述，显示适用版本及来源。

编者归纳不能伪装成原作者结论。包含推断时使用“综合来看”“在这些材料所讨论的条件下”等限定表达，并列出支持该归纳的节点和来源。

短引用只在确有必要保留原措辞时使用；其他内容以准确转述为主。外部来源链接可访问，但网站在离线状态下仍提供足够的来源名称、作者、时间和说明。

## 7. 冲突模型

冲突内容独立建模，分为四类：

1. **定义冲突**：同一术语采用不同边界，例如广义、大众认知和狭义 ACT。
2. **目标冲突**：不同设计目标导致取舍不同，例如高 AI 真实交互与稳定可学习性。
3. **条件差异**：表面矛盾，实际分别适用于 PVE/PVP、清版/非清版、高/低反应频率等不同环境。
4. **直接分歧**：目标和条件接近时仍得出不同判断。

冲突卡必须包含：争议问题、冲突类型、至少两个观点、每个观点的条件和依据、相关案例、来源，以及可选的编者归纳。系统不提供胜负、正确率或权威度排名。

只有同一设计维度的观点才进入冲突卡。不同主题之间的普通关联使用 `related_to`，可比较但不冲突的观点使用 `contrasts_with`，避免制造虚假争议。

图谱中冲突节点同时使用橙色、图标和文字标签，颜色不是唯一识别方式。

## 8. 案例模型与媒体

所有原资料中的游戏示例都必须进入案例清单，包括正文中的详细案例和简短列举。每个案例至少记录：

- 游戏、系列、版本或代际。
- 角色、Boss、敌人或关卡。
- 具体机制和触发条件。
- 产生的战斗结果或体验。
- 支持、反驳或限制的观点。
- 来源和相关媒体。

同一案例可以关联多个概念。例如《仁王2》斋藤利三同时关联低韧性、读指令、精力压制、后摇随机性和立回等主题。

现有 31 个图片/GIF 全部保留，并回到对应论点或案例附近。媒体显示原说明和来源信息；GIF 延迟加载，点击可放大。媒体不在首页一次性加载。图片损坏时显示替代文字和说明，不让缺图破坏正文结构。

## 9. 交互设计

### 9.1 概念星图

概念星图是首页主入口。默认显示中心节点和六个一级知识域。用户点击节点后：

- 该节点成为当前焦点。
- 展开直接子节点和重要横向关系。
- 右侧详情面板显示该节点的分层内容。
- 顶部面包屑保留返回全局和上级节点的路径。
- URL 使用稳定的哈希或查询状态，允许复制链接直接打开特定节点。

悬停或键盘聚焦只显示一句摘要、关系数量、案例数量和冲突数量。复杂关系在选中节点后再出现，避免初始星图成为“毛线团”。

### 9.2 搜索与筛选

搜索覆盖标题、别名、术语、正文、游戏、角色/Boss 和标签。搜索结果不仅显示列表，也在当前图谱中高亮相关节点。

筛选器包括知识域、游戏/系列、概念、冲突类型、来源和复核状态。无结果时显示可清除的筛选条件和相近术语，不出现空白页面。

### 9.3 游戏比较矩阵

比较矩阵是辅助研究工具，行是游戏或系列，列由结构化资料生成，首期包括：

- 类型与框架。
- 主动/被动反应频率倾向。
- 时间、空间和指令精度倾向。
- 主要战斗思路。
- 敌人/Boss 韧性与 AI 框架。
- 外部规则与反馈循环。
- 可读性和表现倾向。

矩阵单元格只显示简短判断。点击后显示判断依据、适用条件、案例和来源，并可跳回相关概念节点。矩阵不是排行榜，不用单一分数概括游戏。

### 9.4 小屏与无障碍

桌面端使用可缩放、可拖动的星图。小屏端自动切换为分层树状列表和抽屉式详情，不强行压缩星图。

所有节点、筛选器、详情面板和媒体放大功能支持键盘操作与清晰焦点状态。界面尊重 `prefers-reduced-motion`。关系与冲突同时使用文字、图标、线型和颜色表达。

## 10. 视觉方向

视觉采用已确认的“战术终端”方向：深色、冷峻、具有游戏分析工具的沉浸感，但不模仿复杂 HUD。

建议基础色：

- 页面背景：接近黑色的深蓝灰。
- 普通表面：略亮的深蓝灰。
- 主文字：低刺激的冷白。
- 次要文字：蓝灰。
- 关系与可探索节点：青绿色。
- 冲突、警示和高关注内容：橙色。
- 分隔线：低对比度蓝灰。

正文面板采用比图谱更平稳的背景和行距，减少长时间阅读疲劳。青绿色只用于交互和关系，橙色只用于冲突与警示，避免整页高饱和。使用本机系统字体，不依赖在线字体。

交互动效以短促的节点聚焦、连线显隐和面板切换为主；不加入持续漂浮、粒子背景或无功能装饰动画。

## 11. 静态生成架构

### 11.1 数据流

1. 维护者新增或修改结构化 Markdown，以及对应媒体。
2. 一键更新入口调用本地生成程序。
3. 生成程序解析元数据和 Markdown，校验关系、来源、案例、冲突和媒体。
4. 程序生成规范化知识数据、图谱数据、游戏矩阵和中文搜索索引。
5. 所有运行时数据被打包进本地脚本或 HTML，不通过 `fetch` 读取本地 JSON，从而兼容 `file://` 离线打开。
6. 完整结果输出到独立网站目录；复制整个目录即可部署。

### 11.2 目录职责

正式实现应保持以下职责边界，具体文件名可在实施计划中微调：

- 原始来源档案。
- 结构化内容目录，按 concepts、games、cases、conflicts、sources 分类。
- 媒体资源目录。
- 生成和校验脚本。
- 网站界面源码。
- 最终静态输出目录。

页面代码不包含人工维护的知识正文。内容更新不要求修改 HTML、CSS 或交互代码。

### 11.3 一键更新

Windows 环境提供可双击运行的更新入口。成功后显示生成时间、节点数、案例数、冲突数、来源数、媒体数和警告摘要。失败时显示具体文件、字段和修复建议。

生成过程先写入临时输出并完成校验，全部成功后再发布为当前版本。失败不覆盖上一个可用版本。

## 12. 校验与错误处理

以下问题阻止发布：

- 重复或缺失 ID。
- 元数据格式错误。
- 必需关系指向不存在的目标。
- 案例缺少游戏、机制、来源或关联概念。
- 冲突卡少于两个观点，或观点缺少来源。
- 引用的本地媒体不存在或无法读取。
- 生成的核心图谱或搜索索引为空。

以下问题产生警告但可以生成：

- 节点没有案例。
- 节点没有任何入边，可能成为孤立节点。
- 外部链接在本地无法验证。
- 来源只有间接整理材料而没有一手链接。
- 术语缺少别名，可能影响搜索命中。

运行时错误采用局部降级：媒体失败显示替代文字；某个节点内容异常时保留图谱其余部分并显示可追踪错误；搜索无结果时提供清除筛选和相近词建议。

## 13. 迁移与完整性审计

现有资料迁移时建立覆盖清单：

- 每篇资料的每个观点段落映射到知识节点、冲突卡、案例或来源说明。
- 被排除的内容记录排除原因，例如重复铺垫、个人联系方式或与设计无关的检索过程。
- 所有游戏名、角色、Boss、关卡和机制举例进入案例候选清单，逐项确认是否已建模。
- 31 个媒体文件逐项记录对应节点、说明和加载状态。

“观点级完整”以覆盖清单为验收依据，而不是以页面字数或是否逐字复制原文判断。

## 14. 验证方案

### 14.1 自动校验

- 内容模式和关系完整性测试。
- ID 唯一性与反向关系生成测试。
- 搜索索引包含中文标题、别名、游戏和角色/Boss 测试。
- 游戏矩阵单元格可回溯到节点和来源测试。
- 31 个媒体文件存在、可读取和可引用测试。
- 离线构建不包含外部运行时依赖测试。

### 14.2 交互验证

- 星图聚焦、缩放、返回全局和深链接。
- 搜索、高亮、筛选、清除和无结果状态。
- 节点详情的三层内容展开。
- 冲突卡双方观点和来源跳转。
- 案例与概念双向跳转。
- 比较矩阵展开依据并返回图谱。
- GIF 延迟加载和媒体放大。
- 键盘导航、焦点状态和减少动画模式。
- 桌面星图与小屏树状列表切换。

### 14.3 人工内容复核

- 按覆盖清单复核 6 篇资料的观点、条件、反例和案例。
- 逐组检查冲突是否确属同一维度，是否误把条件差异当成直接分歧。
- 检查编者归纳是否明确标注且有充分依据。
- 检查矩阵是否表达倾向和条件，而非伪装成精确评分。

## 15. 验收清单

首版完成必须同时满足：

1. 六个一级知识域均有内容并能从首页进入。
2. 6 篇现有资料完成覆盖审计。
3. 所有游戏案例完成索引，详细案例具有机制、结果、观点和来源。
4. 31 个图片/GIF 全部可用且放置正确。
5. 同维度冲突使用冲突卡展示，条件差异不被误标为直接冲突。
6. 编者归纳与来源观点视觉和语义上明确分开。
7. 星图、详情、搜索、筛选、案例索引和比较矩阵可用。
8. 一键更新能够从结构化 Markdown 生成网站。
9. 构建失败不覆盖上一个可用版本。
10. 网站无需联网即可完整阅读，复制整个输出目录即可部署到内网。
